# Validación, benchmarks y métricas

## No hace falta esperar para cambiar el posicionamiento

Se puede usar “lightweight” como filosofía y posicionamiento.

Lo que necesita validación antes de afirmar números concretos son las comparaciones cuantitativas.

---

# Benchmark futuro recomendado

## Herramientas

- Limitcode
- OpenCode
- Claude Code
- Pi
- Cursor
- VS Code + Copilot

## Entorno

Usar:

- misma máquina;
- mismo sistema operativo;
- mismo repositorio;
- mismo modelo cuando sea posible;
- misma tarea;
- mismo periodo de observación.

## Métricas

- RAM idle;
- RAM durante tarea;
- RAM después de 10 min;
- RAM después de 20 min;
- CPU;
- tiempo hasta primer token;
- tiempo hasta primera edición;
- número de procesos;
- estabilidad;
- congelamientos;
- recuperación después de cancelar.

# Métricas de positioning

Registrar objeciones reales:

- “Why not use Claude Code?”
- “Why not use terminal?”
- “Why not Cursor?”
- “What is the differentiator?”
- “Why pay if OSS exists?”
- “Does it support X?”
- “How much RAM does it use?”
- “Does it have diff?”

Si una objeción aparece 3+ veces, debe tener respuesta visible en landing/docs.

# Feedback actual aprendido

Una respuesta de outreach ya reveló:

> “What is your value proposition compared with terminal agents?”

Esto sugiere revisar la landing para explicar la diferencia frente a workflows terminal-first.

No implica que el producto carezca de valor.

Implica que la diferenciación debe hacerse explícita.
